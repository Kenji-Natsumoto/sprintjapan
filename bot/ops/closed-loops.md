# Closed Loop 一覧 v0.1

> 各輪は独立して回る。実行主体（調停役）は一つ。記憶は自社（git と Supabase）。
> 「実行役」はその輪を回すモデルやエージェントの候補。輪ごとに採点して決め、後から差し替えられる。
> 「署名」は夏本本人が固定してから実行する判断。

## 1. X マーケティング

- 目的: 論文、ニュース、イベント、BOT の進捗を X で発信し、問い合わせと登壇機会を生む
- 入力: 公開済みの論文とニュース、開発の進捗ログ（機密を含まないもの）、X 上の反応データ
- 出力: 投稿案（1 日 1〜3 本）、投稿、反応の週次分析、次週の方針
- 頻度: 投稿案は毎日、分析は毎週
- 実行役: 第一候補 Grok（X との近さ）／代替 どのモデルでも可
- 鍵の範囲: X の API のみ
- 機密区分: なし。クライアント名、対話ログ、提案内容は入力に含めない
- 署名が要る判断: 公開投稿（立ち上げから 4 週間は全件。型が固まったら定型投稿は自動、意見表明は署名）
- 成果指標: 問い合わせ数、フォロワーの増分、論文ページへの流入
- 停止条件: 反応が炎上気味（否定的な返信が一定数）、または誤情報の指摘を受けたら自動停止して通知

## 2. サイト発信（sprintjapan.net）

- 目的: 論文、ニュース、テックトレンド速報をサイトに公開し続ける
- 入力: 論文の草稿、ニュースの素材、Drive の速報デッキ
- 出力: ニュース記事、インサイト頁の更新、公開の PR
- 頻度: ニュースは週 1、論文は月 1
- 実行役: 第一候補 Claude Code（このリポジトリで稼働中）／代替 どのモデルでも可
- 鍵の範囲: `Kenji-Natsumoto/sprintjapan` の GitHub、Supabase の news テーブル
- 機密区分: なし
- 署名が要る判断: 公開（main へのマージ）
- 成果指標: 論文の閲覧数、問い合わせ数
- 停止条件: ビルド失敗が連続したら停止して通知

## 3. アプリ開発

- 目的: スーパーボット、lumora-v2、zent などのアプリを設計書と採点ログから継続的に改修する
- 入力: ブリーフ（`bot/day1-brief.md` など）、Issue、採点ログからの改修案、CI の結果
- 出力: PR、テスト結果、変更の要約
- 頻度: 常時（イベント駆動）
- 実行役: 第一候補 Claude Code（稼働中）／代替 他のコーディングエージェントを同じブリーフで採点して比較
- 鍵の範囲: 対象リポジトリごとの GitHub。本番の Secrets は持たない
- 機密区分: 社内
- 署名が要る判断: main へのマージ、本番反映、Secrets の変更
- 成果指標: 受け入れ条件の達成率、修正率の低下（BOT の場合）
- 停止条件: 同じ CI 失敗が 3 回続いたら停止して通知

## 4. BOT 運用ログ分析

- 目的: BOT の対話ログと修正ログから、人格プロンプトと判断規則の改訂案を出す
- 入力: Supabase の `turns` と `override`（点数、夏本ならこう言う、理由、モダリティ判断）、費用と応答時間
- 出力: 週次レポート（修正率、禁止事項違反、問いの重複、図の過不足、費用）、プロンプト改訂案の PR
- 頻度: 日次の集計、週次のレポートと改訂案
- 実行役: どのモデルでも可。改訂案の作成は上位モデル
- 鍵の範囲: Supabase の読み取り専用、`bot/prompts/` への PR 作成
- 機密区分: クライアント。ログは製品の境界の外に出さない。レポートは集計値のみ
- 署名が要る判断: プロンプト改訂の反映
- 成果指標: 修正率の低下、平均点の上昇
- 停止条件: 修正率が前週より悪化したら改訂案を止め、原因分析だけ出す

## 5. クライアント伴走

- 目的: クライアントごとに「今日の一問」を届け、「次の一手」の結果を追い、セッションの記憶を保つ
- 入力: クライアント別ワークスペース（シート、今日の問い、次の一手、対話記憶）、カレンダー
- 出力: 定時チェックインの問い（LINE や通知）、セッションの渡し紙、夏本レビュー要のフラグ
- 頻度: 朝の一問は毎日（頻度上限と静穏時間あり）、セッションは随時
- 実行役: 製品の頭脳（アダプタで差し替え可能。現状 Claude Opus 5）
- 鍵の範囲: Supabase の該当ワークスペースのみ、LINE の送信
- 機密区分: クライアント。他の輪へ出さない
- 署名が要る判断: 高リスクの提言（投資、人事、契約に関わるもの）は夏本レビュー要のフラグを立て、署名後に送る
- 成果指標: 次の一手の実行率、セッション継続率、クライアントの満足
- 停止条件: クライアントが「今は話さない」を押したら当日は停止。3 日連続で無応答なら夏本に通知

## 6. ナレッジ取り込み

- 目的: 公開サイト、SpeakerDeck、Drive、Miro、YouTube の資産を検索可能な形に取り込み、型と事実を分離する
- 入力: sprintjapan.com の REST API、SpeakerDeck の PDF、Drive のスライドと PPTX、Miro のボード、YouTube の文字起こし
- 出力: pgvector への投入、型の抽出（提案の構造、スライド文法、フレームワーク定義）、機密分離の記録
- 頻度: 初回は一括、以後は週 1 の差分
- 実行役: どのモデルでも可
- 鍵の範囲: Drive の読み取り、Miro の読み取り、Supabase の書き込み
- 機密区分: 混在。クライアント名を含む資料は型のみ共通領域へ、事実は該当ワークスペースへ
- 署名が要る判断: 機密分離の規則の変更
- 成果指標: 取り込み件数、検索の的中率（採点セットでの根拠引用の正しさ）
- 停止条件: 機密分離の判定に迷う資料が出たら止めて夏本に確認

## 7. 営業・提案

- 目的: 問い合わせと RFI から、夏本の型（三案比較、リスクと対策、質問形の見出し）で提案書の下書きを作る
- 入力: 問い合わせフォーム、RFI、メールの要件、過去の提案書の型
- 出力: 提案書の下書き（Google スライド）、見積の下書き、返信の下書き
- 頻度: イベント駆動
- 実行役: どのモデルでも可。下書きは上位モデル
- 鍵の範囲: Gmail の読み取り、Drive の書き込み（提案フォルダのみ）
- 機密区分: クライアント
- 署名が要る判断: 送付と価格
- 成果指標: 提案までの日数、受注率
- 停止条件: 価格や条件が判断規則と矛盾する場合は下書きを止めて通知

## 8. 経営ダッシュボード

- 目的: 署名ログ、KPI、各輪の稼働状況を一枚にし、90 日ごとの問い直しを促す
- 入力: 全輪の成果指標、署名ログ、費用
- 出力: 週次の一枚、90 日ごとの 4 つの問い（パーパスに向かっているか、2 年後の像は更新が要るか、AI に任せる領域は正しいか、人がやるべきことに集中できているか）
- 頻度: 週次、90 日
- 実行役: 調停役自身
- 鍵の範囲: Supabase の集計ビューのみ
- 機密区分: 社内
- 署名が要る判断: 90 日の問い直しの結論
- 成果指標: 署名の平均所要時間、輪の停止回数
- 停止条件: なし（この輪は止めない）

## 9. 請求・会計

- 目的: 見積と請求の型（Drive にある）から、月次の請求書と見積書を作る
- 入力: 契約条件、稼働記録、過去の見積と請求
- 出力: 見積書と請求書の PDF、送付の下書き
- 頻度: 月次、イベント駆動
- 実行役: どのモデルでも可
- 鍵の範囲: Drive の該当フォルダ、会計ツールがあればその読み取り
- 機密区分: 社内とクライアント
- 署名が要る判断: 送付、金額
- 成果指標: 請求の遅延ゼロ
- 停止条件: 金額が契約と一致しない場合は止めて通知

---

## 輪をまたぐ規則

1. 輪から輪へ渡してよいのは「集計値」と「公開済みのもの」だけ。生ログは渡さない。
2. 署名待ちの決定は、調停役が一箇所に並べる。夏本はスマホからでも PC からでも同じ列を見る。
3. どの輪も、停止条件に当たったら自動で止まり、理由と再開に必要な判断を一文で通知する。
4. 実行役を差し替えるときは、同じ入力で新旧を並走させ、出力を採点してから切り替える（シャドーモードと同じ手順）。
